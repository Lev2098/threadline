# Масштабування: 1 000 000 повідомлень, 100 000 користувачів на добу

[← README](../../README.md) · [Русский](../ru/scaling.md)

## 1. Оцінка навантаження

| Величина | Розрахунок | Значення |
|---|---|---|
| Користувачів на добу | ТЗ | 100 000 |
| Запитів на користувача | перегляд, сортування, 2–3 гілки, пошук, іноді коментар | ~20 |
| Запитів на добу | 100 000 × 20 | 2 000 000 |
| Середнє навантаження | 2 000 000 / 86 400 | **~23 req/s** |
| Пік (×10, вечірній трафік) | | **~250 req/s** |
| Записів (5% трафіку) | | ~1 req/s у середньому, ~12 req/s у пік |
| Обсяг БД | 1 000 000 × ~0,5 КБ + індекси | ~1 ГБ |
| WebSocket-з'єднань одночасно | ~5% добової аудиторії онлайн | ~5 000 |

**Висновок:** це read-heavy навантаження (95/5). Мільйон рядків — невеликий обсяг для PostgreSQL, *якщо* кожен гарячий запит іде по індексу. Тому архітектура будується навколо: (1) індексів під кожен запит, (2) кешу гарячих сторінок, (3) винесення побічних дій з request path, (4) stateless веб-шару для горизонтального масштабування.

**SLO для навантажувального тесту:** p95 < 200 мс, помилок < 1% на піковому навантаженні.

## 2. Що закладено в архітектуру

### База даних

| Запит | Як виконується | Складність |
|---|---|---|
| Сторінка коренів (будь-яке сортування) | Частковий індекс `WHERE parent_id IS NULL` по `(created_at, id)` / `(lower(username), id)` / `(lower(email), id)` | index scan, 25 рядків |
| Глибока сторінка (OFFSET 100 000) | **Deferred join:** `SELECT id … OFFSET … LIMIT 25` по вузькому індексу, потім `WHERE id IN (…)` | пропускаються записи індексу, а не рядки |
| Уся гілка | `WHERE root_id = ? ORDER BY path` по індексу `(root_id, path)` | 1 range scan |
| Величезна гілка | keyset: `path > :cursor LIMIT 500` | O(сторінки) |
| Лічильник відповідей | денормалізований `replies_count`, `UPDATE … SET n = n + 1` | O(1), без `COUNT(*)` |
| Загальна кількість коренів | лічильник у Redis, `INCR` при новому корені | O(1), без `COUNT(*)` |
| Пошук | Elasticsearch, а не `ILIKE '%…%'` | інвертований індекс |

**Пул з'єднань.** Нативний пул psycopg 3 з обмеженим розміром на процес. Його потребу виявив саме навантажувальний тест, див. розділ 4.

**Read replica.** Якщо задано `POSTGRES_REPLICA_HOST`, вмикається `PrimaryReplicaRouter`: читання йдуть на репліку, записи на primary. Усередині транзакції читання лишаються на primary, тож replication lag не впливає на «щойно записане». Воркер читає з primary явно.

### Кеш (Redis)

- **Сторінки коренів:** кешуються лише **id** перших 10 сторінок кожного сортування (результат дорогого `ORDER BY … OFFSET`). Самі рядки щоразу дочитуються за первинним ключем: 25 PK-lookup коштують ~1 мс, а `replies_count` завжди точний. Тому нова *відповідь* не скидає кеш списку, його скидає лише новий *корінь*.
- **Гілки:** кешується перша порція кожної гілки (без курсора), інвалідація окремо для кожного кореня. Порції за курсором не кешуються, щоб довільні курсори не засмічували Redis.
- **Інвалідація версіями** (`roots:ver`, `thread:{id}:ver`) за O(1). Версія піднімається **після commit**.
- `IGNORE_EXCEPTIONS`: якщо Redis недоступний, система деградує до БД і не падає.

### Асинхронність (RabbitMQ + Celery)

На шляху запиту лишається лише те, що потрібно для відповіді: валідація, капча, ресайз і `INSERT`. Push у WebSocket та індексація в Elasticsearch виконуються у воркері. Задачі мають `acks_late`, retry з експоненційним backoff і `reject_on_worker_lost`, тож падіння воркера не губить подій.

### Веб-шар і WebSocket

- **HTTP і WebSocket розділено на два сервіси з одного образу.** `backend` — це gunicorn (WSGI, `gthread`): `WEB_CONCURRENCY` процесів × `WEB_THREADS` потоків. `realtime` — це uvicorn (ASGI, Channels) лише для `/ws/`. nginx маршрутизує за шляхом. Чому так, показав навантажувальний тест (розділ 4).
- Обидва сервіси stateless: `--scale backend=N`, `--scale realtime=M` незалежно.
- WebSocket fan-out через Redis channel layer: подію отримують усі репліки `realtime`, і кожна віддає її своїм клієнтам. 5 000 з'єднань для ASGI — це кілька десятків МБ RAM.
- Клієнт перепідключається з експоненційною затримкою та jitter, щоб уникнути thundering herd після рестарту.

### Edge (nginx)

- Статика SPA з `immutable`-кешем, gzip, медіа без участі Python.
- `limit_req` per-IP (окремо для читання і запису) відсікає ботів до Django.
- DRF-throttles per-client (JWT) працюють як другий рубіж.

## 3. Як запустити навантажувальний тест

```bash
./loadtest/run.sh            # 1 000 000 коментарів + індекс ES + Locust 3 хв, 300 користувачів
```

Скрипт:
1. піднімає стек з оверлеєм `docker-compose.loadtest.yml` (вимкнені throttles і фіксована відповідь капчі; **лише для тесту**);
2. генерує 1 000 000 коментарів (`seed_comments`, ~14 000 рядків/с);
3. індексує їх в Elasticsearch;
4. запускає Locust: суміш 95% читання і 5% запису, як у розрахунку вище;
5. завершується з кодом 1, якщо SLO не виконано (p95 > 200 мс або помилок > 1%), тому його можна підключити в CI.

Звіт: `loadtest/reports/report.html` і CSV у тій самій папці.

## 4. Результати

Середовище: ноутбук, Docker Desktop VM з **8 vCPU / 8 ГБ на все одразу**: PostgreSQL, Redis, RabbitMQ, Elasticsearch, backend, realtime, worker, nginx і сам генератор навантаження Locust. На виділеному сервері запас буде більшим.

Дані: **1 015 712 коментарів**, з них 305 210 заголовних, таблиця з індексами займає 539 МБ. Профіль: 300 віртуальних користувачів із паузами 0,5–3 с, суміш 95% читання і 5% запису, 3 хвилини.

### Фінальний результат

| Ендпоінт | p50 | p95 | p99 | Запитів |
|---|---|---|---|---|
| `GET /comments?page=1` | 3 мс | 8 мс | 24 мс | 12 591 |
| `GET /comments` (сортування, сторінки 1–10) | 4 мс | 9 мс | 26 мс | 4 694 |
| `GET /comments` (глибокі сторінки, будь-яке сортування) | 14 мс | 26 мс | 48 мс | 1 587 |
| `GET /comments/:id/thread` | 3 мс | 7 мс | 17 мс | 7 826 |
| `GET /comments/search` (Elasticsearch) | 12 мс | 20 мс | 36 мс | 1 571 |
| `POST /comments` (запис + подія) | 6 мс | 12 мс | 21 мс | 1 597 |
| **Разом** | **4 мс** | **16 мс** | **29 мс** | **31 763** |

**177 req/s, 0 помилок, SLO виконано** (p95 16 мс при цілі < 200 мс). CPU під навантаженням: backend ~0,7 ядра, PostgreSQL ~0,2 ядра.

**Стрес-тест** (конфігурація ітерації 4): 1000 користувачів дали **580 req/s** (у 2,3 раза більше за розрахунковий пік), 0 помилок, p50 9 мс, p95 65 мс, p99 150 мс.

### Що знайшов тест і що виправлено

Тест прогнали кілька разів. Кожна ітерація знаходила реальну проблему, яку на 5 000 записів не видно:

| # | Стан | p50 | p95 | p99 | Помилки | Знахідка → виправлення |
|---|---|---|---|---|---|---|
| 1 | ASGI + `CONN_MAX_AGE` | — | — | — | ~30% | `FATAL: too many clients`: під ASGI кожен потік тримав власне з'єднання → **обмежений пул psycopg 3** |
| 2 | + пул з'єднань | 21 мс | 350 мс | 1,2 с | 0% | PostgreSQL 227% CPU: кожна відповідь скидала кеш першої сторінки, і `COUNT(*)` по 300 тис. рядків рахувався знову → **кешуємо id сторінки, рядки беремо за PK, лічильник через `INCR`, список скидає лише новий корінь** |
| 3 | + новий кеш | 13 мс | 470 мс | 1,2 с | 0% | PostgreSQL 23% CPU, але backend 3 ядра і рівний хвіст навіть у `/session`: sync-view під ASGI → **HTTP через gunicorn (WSGI, потоки), WebSocket через uvicorn (ASGI)** |
| 4 | + gunicorn / uvicorn | 4 мс | 15 мс | 28 мс | 0,03% | Рідкісні `Connection reset`: перезапуск воркерів за `max-requests` і гонка keep-alive → **keep-alive gunicorn довший, ніж у nginx** |
| 5 | + глибокі сторінки з будь-яким сортуванням | 4 мс | 16 мс | 29 мс | 0% | `EXPLAIN` показав 1,7 с на `OFFSET 150000` за username: функціональний індекс не давав index-only scan → **`INCLUDE (username)` / `INCLUDE (email)`** |

### Плани запитів на 1M рядків

| Запит | План | Час |
|---|---|---|
| Сторінка 6000 за датою (`OFFSET 150000`) | Index Only Scan `comments_root_created_idx` | 94 мс (холодний кеш) |
| Сторінка 6000 за username | Index Only Scan `comments_root_username_idx` | 1,7 с → **45 мс** |
| Сторінка 6000 за e-mail | Index Only Scan `comments_root_email_idx` | **53 мс** |
| Уся гілка | Index Scan `comments_thread_path_idx` | 1,6 мс |

## 5. Наступні кроки, якщо навантаження зросте в 10 разів

| Вузьке місце | Рішення |
|---|---|
| CPU веб-шару | `--scale backend=N` або Kubernetes HPA: шар stateless, нічого переробляти не треба |
| Кількість WebSocket | `--scale realtime=M` незалежно від HTTP |
| З'єднання з БД | PgBouncer у transaction mode перед PostgreSQL |
| Читання з БД | 1–2 read replicas (роутер уже є) |
| Запис | Записів ~12/с у пік; один primary PostgreSQL тримає тисячі. Шардинг за `root_id` має сенс лише при порядках більших обсягах |
| Медіа | `STORAGES` → S3 / DigitalOcean Spaces + CDN; код не змінюється (`DjangoFileStorage`) |
| Кеш | Redis Cluster або окремі інстанси для кешу та channel layer |
| WebSocket | Окремий пул ASGI-реплік лише під `/ws/` (уже виділено в сервіс `realtime`) |
| Пошук | Кластер Elasticsearch з 3 нод і репліками індексу |
