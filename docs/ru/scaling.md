# Масштабирование: 1 000 000 сообщений, 100 000 пользователей в сутки

[← README](../../README.ru.md) · [Українська](../uk/scaling.md)

## 1. Оценка нагрузки

| Величина | Расчёт | Значение |
|---|---|---|
| Пользователей в сутки | ТЗ | 100 000 |
| Запросов на пользователя | просмотр, сортировка, 2–3 ветки, поиск, иногда комментарий | ~20 |
| Запросов в сутки | 100 000 × 20 | 2 000 000 |
| Средняя нагрузка | 2 000 000 / 86 400 | **~23 req/s** |
| Пик (×10, вечерний трафик) | | **~250 req/s** |
| Записей (5% трафика) | | ~1 req/s в среднем, ~12 req/s в пик |
| Объём БД | 1 000 000 × ~0,5 КБ + индексы | ~1 ГБ |
| WebSocket-соединений одновременно | ~5% суточной аудитории онлайн | ~5 000 |

**Вывод:** это read-heavy нагрузка (95/5). Миллион строк — небольшой объём для PostgreSQL, *если* каждый горячий запрос идёт по индексу. Поэтому архитектура строится вокруг: (1) индексов под каждый запрос, (2) кэша горячих страниц, (3) выноса побочных действий из request path, (4) stateless веб-слоя для горизонтального масштабирования.

**SLO для нагрузочного теста:** p95 < 200 мс, ошибок < 1% на пиковой нагрузке.

## 2. Что заложено в архитектуру

### База данных

| Запрос | Как выполняется | Сложность |
|---|---|---|
| Страница корней (любая сортировка) | Частичный индекс `WHERE parent_id IS NULL` по `(created_at, id)` / `(lower(username), id)` / `(lower(email), id)` | index scan, 25 строк |
| Глубокая страница (OFFSET 100 000) | **Deferred join:** `SELECT id … OFFSET … LIMIT 25` по узкому индексу, затем `WHERE id IN (…)` | пропускаются записи индекса, а не строки |
| Вся ветка | `WHERE root_id = ? ORDER BY path` по индексу `(root_id, path)` | 1 range scan |
| Огромная ветка | keyset: `path > :cursor LIMIT 500` | O(страницы) |
| Счётчик ответов | денормализованный `replies_count`, `UPDATE … SET n = n + 1` | O(1), без `COUNT(*)` |
| Общее количество корней | счётчик в Redis, `INCR` при новом корне | O(1), без `COUNT(*)` |
| Поиск | Elasticsearch, а не `ILIKE '%…%'` | инвертированный индекс |

**Пул соединений.** Нативный пул psycopg 3 с ограниченным размером на процесс. Его необходимость выявил именно нагрузочный тест, см. раздел 4.

**Read replica.** Если задан `POSTGRES_REPLICA_HOST`, включается `PrimaryReplicaRouter`: чтения идут на реплику, записи на primary. Внутри транзакции чтения остаются на primary, поэтому replication lag не влияет на «только что записанное». Воркер читает с primary явно.

### Кэш (Redis)

- **Страницы корней:** кэшируются только **id** первых 10 страниц каждой сортировки (результат дорогого `ORDER BY … OFFSET`). Сами строки каждый раз дочитываются по первичному ключу: 25 PK-lookup стоят ~1 мс, а `replies_count` всегда точный. Поэтому новый *ответ* не сбрасывает кэш списка, его сбрасывает только новый *корень*.
- **Ветки:** кэшируется первая порция каждой ветки (без курсора), инвалидация отдельно для каждого корня. Порции по курсору не кэшируются, чтобы произвольные курсоры не засоряли Redis.
- **Инвалидация версиями** (`roots:ver`, `thread:{id}:ver`) за O(1). Версия поднимается **после commit**.
- `IGNORE_EXCEPTIONS`: если Redis недоступен, система деградирует до БД и не падает.

### Асинхронность (RabbitMQ + Celery)

На пути запроса остаётся только то, что нужно для ответа: валидация, капча, ресайз и `INSERT`. Push в WebSocket и индексация в Elasticsearch выполняются в воркере. Задачи с `acks_late`, retry с экспоненциальным backoff и `reject_on_worker_lost`, поэтому падение воркера не теряет событий.

### Веб-слой и WebSocket

- **HTTP и WebSocket разделены на два сервиса из одного образа.** `backend` — это gunicorn (WSGI, `gthread`): `WEB_CONCURRENCY` процессов × `WEB_THREADS` потоков. `realtime` — это uvicorn (ASGI, Channels) только для `/ws/`. nginx маршрутизирует по пути. Почему так, показал нагрузочный тест (раздел 4).
- Оба сервиса stateless: `--scale backend=N`, `--scale realtime=M` независимо.
- WebSocket fan-out через Redis channel layer: событие получают все реплики `realtime`, и каждая отдаёт его своим клиентам. 5 000 соединений для ASGI — это несколько десятков МБ RAM.
- Клиент переподключается с экспоненциальной задержкой и jitter, чтобы избежать thundering herd после рестарта.

### Edge (nginx)

- Статика SPA с `immutable`-кэшем, gzip, медиа без участия Python.
- `limit_req` per-IP (отдельно для чтения и записи) отсекает ботов до Django.
- DRF-throttles per-client (JWT) работают как второй рубеж.

## 3. Как запустить нагрузочный тест

```bash
./loadtest/run.sh            # 1 000 000 комментариев + индекс ES + Locust 3 мин, 300 пользователей
```

Скрипт:
1. поднимает стек с оверлеем `docker-compose.loadtest.yml` (выключены throttles и фиксированный ответ капчи; **только для теста**);
2. генерирует 1 000 000 комментариев (`seed_comments`, ~14 000 строк/с);
3. индексирует их в Elasticsearch;
4. запускает Locust: смесь 95% чтения и 5% записи, как в расчёте выше;
5. завершается с кодом 1, если SLO не выполнено (p95 > 200 мс или ошибок > 1%), поэтому его можно подключить в CI.

Отчёт: `loadtest/reports/report.html` и CSV в той же папке.

## 4. Результаты

Среда: ноутбук, Docker Desktop VM с **8 vCPU / 8 ГБ на всё сразу**: PostgreSQL, Redis, RabbitMQ, Elasticsearch, backend, realtime, worker, nginx и сам генератор нагрузки Locust. На выделенном сервере запас будет больше.

Данные: **1 015 712 комментариев**, из них 305 210 заглавных, таблица с индексами занимает 539 МБ. Профиль: 300 виртуальных пользователей с паузами 0,5–3 с, смесь 95% чтения и 5% записи, 3 минуты.

### Финальный результат

| Эндпоинт | p50 | p95 | p99 | Запросов |
|---|---|---|---|---|
| `GET /comments?page=1` | 3 мс | 8 мс | 24 мс | 12 591 |
| `GET /comments` (сортировка, страницы 1–10) | 4 мс | 9 мс | 26 мс | 4 694 |
| `GET /comments` (глубокие страницы, любая сортировка) | 14 мс | 26 мс | 48 мс | 1 587 |
| `GET /comments/:id/thread` | 3 мс | 7 мс | 17 мс | 7 826 |
| `GET /comments/search` (Elasticsearch) | 12 мс | 20 мс | 36 мс | 1 571 |
| `POST /comments` (запись + событие) | 6 мс | 12 мс | 21 мс | 1 597 |
| **Итого** | **4 мс** | **16 мс** | **29 мс** | **31 763** |

**177 req/s, 0 ошибок, SLO выполнено** (p95 16 мс при цели < 200 мс). CPU под нагрузкой: backend ~0,7 ядра, PostgreSQL ~0,2 ядра.

**Стресс-тест** (конфигурация итерации 4): 1000 пользователей дали **580 req/s** (в 2,3 раза больше расчётного пика), 0 ошибок, p50 9 мс, p95 65 мс, p99 150 мс.

### Что нашёл тест и что исправлено

Тест прогнали несколько раз. Каждая итерация находила реальную проблему, которую на 5 000 записях не видно:

| # | Состояние | p50 | p95 | p99 | Ошибки | Находка → исправление |
|---|---|---|---|---|---|---|
| 1 | ASGI + `CONN_MAX_AGE` | — | — | — | ~30% | `FATAL: too many clients`: под ASGI каждый поток держал своё соединение → **ограниченный пул psycopg 3** |
| 2 | + пул соединений | 21 мс | 350 мс | 1,2 с | 0% | PostgreSQL 227% CPU: каждый ответ сбрасывал кэш первой страницы, и `COUNT(*)` по 300 тыс. строк пересчитывался → **кэшируем id страницы, строки берём по PK, счётчик через `INCR`, список сбрасывает только новый корень** |
| 3 | + новый кэш | 13 мс | 470 мс | 1,2 с | 0% | PostgreSQL 23% CPU, но backend 3 ядра и ровный хвост даже у `/session`: sync-view под ASGI → **HTTP через gunicorn (WSGI, потоки), WebSocket через uvicorn (ASGI)** |
| 4 | + gunicorn / uvicorn | 4 мс | 15 мс | 28 мс | 0,03% | Редкие `Connection reset`: перезапуск воркеров по `max-requests` и гонка keep-alive → **keep-alive gunicorn длиннее, чем у nginx** |
| 5 | + глубокие страницы с любой сортировкой | 4 мс | 16 мс | 29 мс | 0% | `EXPLAIN` показал 1,7 с на `OFFSET 150000` по username: функциональный индекс не давал index-only scan → **`INCLUDE (username)` / `INCLUDE (email)`** |

### Планы запросов на 1M строк

| Запрос | План | Время |
|---|---|---|
| Страница 6000 по дате (`OFFSET 150000`) | Index Only Scan `comments_root_created_idx` | 94 мс (холодный кэш) |

## 5. Следующие шаги при росте нагрузки в 10 раз

| Узкое место | Решение |
|---|---|
| CPU веб-слоя | `--scale backend=N` или Kubernetes HPA: слой stateless, ничего переделывать не нужно |
| Количество WebSocket | `--scale realtime=M` независимо от HTTP |
| Соединения с БД | PgBouncer в transaction mode перед PostgreSQL |
| Чтение из БД | 1–2 read replicas (роутер уже есть) |
| Запись | Записей ~12/с в пик; один primary PostgreSQL держит тысячи. Шардинг по `root_id` имеет смысл только при объёмах на порядки больше |
| Медиа | `STORAGES` → S3 / DigitalOcean Spaces + CDN; код не меняется (`DjangoFileStorage`) |
| Кэш | Redis Cluster или отдельные инстансы для кэша и channel layer |
| WebSocket | Отдельный пул ASGI-реплик только под `/ws/` (уже выделен в сервис `realtime`) |
| Поиск | Кластер Elasticsearch из 3 нод с репликами индекса |
